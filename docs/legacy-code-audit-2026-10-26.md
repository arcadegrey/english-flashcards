## 1. P1：冲突同步响应可能覆盖请求期间的新学习记录

位置：`src/App.jsx:1028` 的 `pushProgressToCloud`，尤其 `1070–1076` 的冲突响应处理。

发起上传时截取 `progressToSync`，但服务端返回 `conflictResolved` 后，直接把响应中的旧快照交给 `applyMergedProgress`。请求期间的本机变化只用于差异判断，没有重新合并进将要应用的状态。该调用还会把旧快照写回本机存储。

隔离复现使用源码中的实际回调，控制网络返回顺序：

1. 上传本机已学列表 `[1]`，请求等待。
2. 本机继续学习，当前列表成为 `[1, 2]`。
3. 服务器合并另一设备的数据，响应 `[1, 3]`，并标记冲突已解决。
4. 客户端应用 `[1, 3]`，请求期间新增的 `2` 被移除。

此复现针对同一账号，不是账号串用，也不是已知的“多设备日计数取最大值”限制。真实触发条件是响应发生冲突，且本机在等待期间继续学习；尚未用真实账号或完整浏览器流程验收。

优化方向：抽出独立的进度同步协调层，记录发出快照及本机修订版本；响应返回时保留请求发出后的本机变化，并在需要时再次同步。多个上传应串行或明确处理响应顺序。不能只把所有列表无条件做并集，否则会破坏移除标记、清空进度等操作。保留现有 expected-user 校验、复习时间戳、偏好时间戳、收藏删除标记及日计数合并规则。

必要回归：延迟响应期间继续学习、两个上传逆序返回、收藏取消、计划切换、显式清空、切换账号与网络恢复。

## 2. P2：语音取消没有覆盖异步请求和播放 Promise 生命周期

位置：`src/utils/speech.js:280`、`182`、`466`。

`stopSpeak()` 只取消当前浏览器合成并暂停当前 Audio；Kokoro 请求没有 AbortSignal，也没有播放请求代次校验。调用停止后，旧请求仍可完成并进入 `playAudioBlob`，重新启动播放。连续发起两个朗读时也缺少防止旧响应抢占新音频的机制。

另一个相关问题是 `playAudioSource` 的 Promise 仅在 ended/error/play 拒绝时结束，暂停和清空引用不会主动结算。隔离复现确认：播放后调用停止，Audio 已暂停，但调用方的 Promise 仍未结束。等待它的界面可能保留“试听中”等状态。

优化方向：统一管理语音请求的代次、AbortController、当前播放和 Promise 清理；停止或新播放应让旧调用有明确的取消结果，取消不能触发浏览器语音回退。自然结束、播放失败、切换音色、切换页面也应走同一清理流程。

必要回归：停止后网络才返回、旧响应晚于新响应、播放中取消、取消后再次播放、真正播放错误时的回退。

## 3. P2：静态音频与回退路径的语速不一致

位置：`src/utils/speech.js:182`、`392`、`418`、`442`；可见设置入口在 `VoiceSettings.jsx` 和 `QuickMenu.jsx`。

已隔离复现两种现象：

- 将 Kokoro 语速设为 `0.5`，成功命中静态 MP3 时，Audio 的 `playbackRate` 仍为默认 `1`。静态词头和例句分支均没有接收语速参数，因此设置及慢速选项对这些播放没有生效。
- 将全局语速设为 `0.8`，直接 `speak()` 的浏览器朗读为 `0.8`；`speakWord()`／`speakExample()` 经由 `speak()` 时变成约 `0.64`。原因是包装函数和通用函数各乘了一次全局语速。默认 `1.0` 以及最低速度的截断可能掩盖这个问题。

优化方向：明确全局语速、Kokoro 设置和单次调用 rate 的组合规则，只计算一次有效语速；静态 MP3、动态 Kokoro 和浏览器合成消费同一个结果。静态音频可通过 playbackRate 实现，不需要重新生成整库录音或修改版本 URL。

必要回归：两种设置入口、静态词头、静态例句、静态失败后动态生成、动态失败后浏览器合成，以及 `0.5`／`0.8`／`1.0`／`1.5` 的边界。

## 4. P2：题目组件每次重渲染都重新生成并丢弃整轮题目

位置：`src/components/Quiz.jsx:44`、`FillBlank.jsx:87`、`MatchingTest.jsx:32`。

三个组件都在组件函数体中执行 `const initialRound = create...Round(vocabulary)`，随后才通过 useState 的初始化函数读取它。useState 不会重复初始化，但前面的整轮生成仍会在每次重渲染发生。

使用当前 8699 条完整词库，执行实际工厂和组件初始化代码，保留 useState 的既有值后再运行一次，三个组件都额外发生约 **19 万次 Math.random 调用**。计数随随机排序变化，不是固定性能预算，也不是浏览器 FPS 测量。连线题的 pointer move 会更新状态，因此无效整库排序不只发生在答题时。

优化方向：用单个惰性初始化的 round 状态承载题目、选项、句子和错误，仅在换题、换范围或开始新一组时生成。再将重复的随机抽样收口，避免为抽取少数候选而对全库多次随机排序；如替换排序实现，应使用明确的洗牌／抽样算法。保留同词头去重、可测试范围过滤和作业规则。

必要回归：重渲染不重抽题、范围变更才重置、同词头不当干扰项、空词库、填空无可用例句、连线拖动、20 次答题上限及草稿续答。

## 5. P3：App 主组件和重复派生数据可分批整理

`src/App.jsx` 当前 3102 行，集中了导航历史、词库分片、计划任务、认证、进度同步和学习事件。文件长度本身不构成缺陷；第 1 项说明同步状态机缺少可独立验证的边界，是优先抽离的职责。

另有两个具体维护点：

- `App.jsx:470` 的阅读元数据计算依赖 mastered ID 集合。每次“标记认识”变化，都会重新分词全部文章并做词库查找。可以分离“文章静态词数／预计时间”“依赖词库版本的关联词 ID”“依赖个人进度的未认识数”。目前仅为代码路径确认，未测得用户可感知的耗时，优先级低于前四项。
- 进度归一化分散在 App、`src/utils/workerAuth.js` 和 `worker/index.js`。逐步提取共享纯模型前，应列清现有字段、去重和优先级差异，用兼容测试固定契约，再合并真正相同的部分。

推荐拆分顺序：同步协调层 → 词库加载／分类模型 → 导航历史 → 学习事件 reducer。按模块交付，避免一次性重写 3000 行。

`storage.updateWordProgress`、`storage.recordStudySession` 及 `cloudAuth.js` 兼容导出在当前源码搜索中没有调用方，可列入后续删除候选；应在确认历史兼容和外部脚本引用后再删除。退役词条、历史音频映射和旧数据适配不属于这类清理对象。
