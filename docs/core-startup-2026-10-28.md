# 核心目录提前准备与词库索引分层（2026-10-28）

## 范围与行为

继续性能审查第 3 项，处理核心目录在应用代码之后才开始请求，以及完整词库定位数据进入首页启动链的问题。保留上一批全部未提交改动，不更改学习流程、评分、复习、记录、账号隔离或同步格式。

首页仍需要完整有效的核心目录后才显示原今日计划；本轮没有提前渲染可操作的残缺任务、假进度或另造 shell。阅读正文／元数据分层、非关键插画、分类增量与 CSS 拆分仍留待后续。

## 启动边界

- `index.html` 改为 `src/bootstrap.js`：先沿用原 `flashcards_theme` 偏好，再调用核心目录准备，并立即动态导入原 `main.jsx`。StrictMode、React root、App 与现有布局均不变。
- 核心请求复用 `vocabularyStartup.js` 的唯一 `createVocabularyLoader` 实例；App 后续使用同一个实例、验证函数与 pending/memory map。没有插入绕过 CacheStorage 的 HTML 数据 preload。冷启动只下载一次核心摘要，热缓存不会因提前准备额外下载。
- 原版本化 `flashcards-vocabulary-*` 缓存名、URL、300ms 缓存读取回退、20 秒无接收进度超时、缓存维护及旧完整 core/full 文件兼容保持不变。提前失败不会留下已拒绝的缓存请求或未处理 rejection；App 仍执行原来的加载／错误／显式重试，没有无限自动重试。
- 主题恢复移入 `initialTheme.js`，仍只读原偏好；应用 JS/CSS 不可用时显示与原 PageLoadBoundary 相同的错误文字和刷新按钮，保留键盘焦点与本机数据。无自动刷新循环。

原 `vocabularyIndex.json` 完整保留，源内容未修改。原生成命令 `node scripts/build-vocabulary-delivery.mjs` 额外生成两份源码元数据，仍由既有 predev/prebuild 调用：

| 元数据 | 源 JSON 字节 | 内容与使用时机 |
| --- | ---: | --- |
| `vocabularyStartup.json` | 3205 | 精确活动 ID 集合的连续段编码、真实计数、core／extension 目录条目；启动可用 |
| `vocabularyDetailsIndex.json` | 10487 | 原 50 词例句批次的全部定位；明确开始学习时轻量预热或实际例句请求时加载 |
| 原 `vocabularyIndex.json` | 95914 | 完整 ID → List／旧完整文件定位、目录等；按 ID 恢复、List 范围及旧完整 API 实际需要时导入 |

连续段由构建时的全部 8699 个真实活动 ID 精确生成，保留 327 个退役空洞；运行时不凭固定范围、拼写或类别推断成员关系。测试遍历全部 ID 和数字／字符串／非规范输入，保持原字符串键语义。

- `loadVocabularyCatalogEntry` 共用原 count／唯一 ID／活动成员／word／meaning 验证，以及旧完整文件的优先缓存读取。
- `createFullVocabularyCatalogLoader` 只需已知 core／extension 条目，即可准备完整 8699 摘要；不等大型 ID/List 索引。完整数量、合并顺序、旧完整 full 缓存、并发结果复用和失败重试沿用原实现。
- `createVocabularyDetailsLoader` 从原 delivery service 提取同一份例句验证／缓存逻辑。稳定身份仍是 ID + 精确词头；保留双语例句、同步 `peekWordDetails`、50 词共享请求、自定义／退役内联例句和 cache-only 旧文件回退。
- `loadAllExamVocabulary` 在明确开始学习／测试时并行预热小例句索引，与学习页代码和完整摘要重叠；普通全范围学习不会因此导入大型 ID/List 索引。目录／页面完整性仍决定是否进入学习；例句继续沿用原按需加载、失败提示与重试。
- 需要 List／按 ID 恢复时，完整定位索引的并发导入共享且失败可重试。已经有完整索引的范围会话直接沿用原 delivery service 的例句定位与缓存。
- 旧 `loadVocabulary`、`loadFullVocabulary`、List API 与完整字段仍保留。空／未知／退役 ID 不为查不到的词下载全库。新例句索引模块失败时，可从已经缓存的完整 core／extension／full 恢复原例句，保持同步 peek；后续未缓存词仍可重试小索引。
- 原完整核心并未覆盖全部日常／四六级；本轮没有跳过既有分类补载检查，也没有将只加载核心误标成全库完整。

## 性能测量

首次实验将整个 delivery code／index 都动态化，但发现学习入口出现串行等待。最终保留轻量加载代码，拆出独立完整摘要路径与小例句索引，不把大型定位索引放到普通词卡必经链。实验日志留存，以下只以最终代码报告结果。

沿用原 gzip 服务器、按 cookie 共享 256000 B/s + 100ms 或 64000 B/s + 150ms、390×844、CPU 4 倍降速、减少动态效果、HTTP 缓存关闭、SW 阻止、新上下文。正式启动与第一次学习各组中速 3 次取中位，慢速各 1 次。核心摘要仍为原文件，冷启动各场景均只有一次核心请求。

先沿用审查脚本的“自动操作前标记”。最终同条件结果：首页中速 1.689 → 1.601s，慢速 6.260 → 5.810s。脚本从 DOM 等待返回到按钮点击还包含自动化等待，因此另建实际 click capture 对照，保留两套数据，不用更有利的一个掩盖另一个。

实际点击对照的基线为隔离临时构建：复制本轮开始时其他工作内容，只将本轮修改的入口／词库加载模块恢复为 HEAD 对应源文件，使用原项目 envDir 与同一 Vite 配置；不覆盖真实工作区。生成器未改动 canonical 数据。前后都在实际 button click 的捕获阶段记录时点。

单位秒，中速各 3 次中位，慢速各 1 次：

| 场景 | 核心请求开始 | 核心结束 | 首页 DOM | 首页 DOM → 实际点击 | 点击 → 词卡 | 点击 → 例句 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 修改前，中速 | 1.099 | 1.653 | 1.698 | 0.207 | 2.162 | 2.296 |
| 修改后，中速 | 0.243 | 1.530 | 1.580 | 0.498 | 2.266 | 2.409 |
| 修改前，慢速 | 3.665 | 6.210 | 6.256 | 0.226 | 8.035 | 9.540 |
| 修改后，慢速 | 0.348 | 5.756 | 5.819 | 0.376 | 7.977 | 9.485 |

已确认核心请求更早并与应用代码重叠，首页中速中位提前 0.118s（约 6.9%），慢速单次提前 0.437s（约 7.0%）。共享带宽下核心自身下载持续时间变长，不把请求提前量直接当作用户节省时间。

实际点击至词卡中速中位增加 0.104s，慢速单次减少 0.058s；例句对应增加 0.113s／减少 0.055s。导航至词卡的原始时点中速 4.061 → 4.357s、慢速 14.517 → 14.172s，包含不同的自动等待／点击时机。**本轮不是整条学习路径全面提速，也不能把两个独立中位数相加作为真实端到端承诺。** 后续仍应处理图片带宽与请求调度。

实际点击场景里，首页 DOM 前的 `/assets/*.js` HTTP gzip 正文合计 183057 → 160277 B，约少 12.4%；文件数 15 → 30。这个口径涵盖首页当次已启动的资产脚本，不代表全站或所有路径的总流量。数据地址与例句文本未变化；没有把入口文件变小误报为全部代码减少。

两套正式前后计时合计 16 个上下文无 pageerror。非正式实验未计入通过数量。这些都是本机 DOM／事件时点，不是 LCP、Lighthouse、Safari 或中国真实手机网络结果。PWA 仍沿用代码预缓存：72 → 91 项，约 1792.79 → 1812.57 KiB 未压缩产物；首次安装流量未因此减少，不在本轮承诺首次安装提速。
