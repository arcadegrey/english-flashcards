# 分类计划增量补载（2026-10-28）

完成性能审查第 5 项。此前任何非 all 计划都会下载完整扩展摘要；开始背词和四种测试也共用全库准备。现在按当前计划补齐相对启动核心目录的缺失词条，完整后才开放原有学习入口；没有修改界面、学习算法、词库内容或用户记录。

## 加载与完整性边界

- 构建脚本从相同 canonical 全库和 core 生成五份带内容 hash 的分类增量，以及独立的精确分类 ID 范围索引。3495 条启动 core、5204 条完整扩展、原 List／例句摘要和启动索引均保持原产物。`predev`／`prebuild` 仍负责生成；没有手工维护另一份词库。
- 分类索引与加载器仅在非 all 计划需要补载时动态导入，正常分类请求不需要大型 ID／List 定位索引。分类索引 JSON 为 28065 B／6383 B gzip；实际构建 JS chunk 为 6519 B gzip，分类加载器 chunk 为 805 B gzip。这些额外代码不能算作零成本，也不能把表中词库摘要大小当作整条路径全部流量。
- 加载器验证分类和缺失部分的精确 ID 成员、去重、数量、分类及必需文本。并发调用共享准备，失败释放重试。结果为完整当前分类；采用前仍保留页面／账号／计划代次校验，活动词卡池仍保持稳定。
- 计划就绪根据已验证公共目录的去重分类数量及尚缺的已记录 ID 重新计算，不持久化完成标志；自定义词不会填补公共目录缺口。分类准备和分类学习不再设置 `fullVocabularyLoadedRef`。切回 all 后显式开始仍通过原完整目录 API 校验 8699 条，代码与数据仍并行准备。
- 计划准备完成分类后，再补分类之外仍缺失的已学、认识、复习进度和错词 ID，避免同分类记录重复下载 List。全局复习和错词仍可使用这些记录；退役／自定义 ID 仍沿用原有边界。目录尚未加载或可选 manifest 失败时，统计分母使用生成的全库计数，不把局部目录大小当总词数。
- 旧扩展摘要、完整扩展、旧完整全库缓存优先复用。新分类文件失败时，按缺失 ID 调用原 List 恢复 API，支持仅有旧 List 缓存的离线安装；普通成功路径不加载旧定位索引。缺少任何可恢复数据时仍显示现有错误和重试，不展示不完整学习池。
- 本批不拆除完整 core 门控，也没有提前完成今日任务、改造同步协议、迁移用户存储或更新 Worker／D1。
